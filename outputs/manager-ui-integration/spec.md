# 经理版前端与功能整合 Spec

## 1. 目标

以经理提供的管理后台和原生微信小程序作为产品与视觉基准，在当前 `yuqi` 项目中重新实现。当前项目继续作为技术底座，保留现有 PocketBase、Node 网关/任务进程、人工复核、整改闭环、租户与数据范围控制等能力。

最终用户看到的是经理版的信息架构、页面布局、字段、操作入口和业务模块；底层不复制经理包中的单文件 Python、SQLite 或静态 `admin.html`。

## 2. 已确定的产品原则

1. 管理后台的导航、页面结构、视觉和可见功能，以经理版为准；能一致就不另做设计。
2. 当前项目已有但经理版页面未完整表达的闭环能力，合并到对应页面的标签页、详情区或操作区，不删除。
3. 当前处于测试阶段，微信手机号登录和培训中心按完整目标建设；后端暂缺不是砍功能的理由。
4. AI 巡检结果始终是“疑似风险”，必须经过人工复核后才可推送员工整改。
5. 原生微信小程序纳入交付范围，不以 H5 替代。

## 3. 目标信息架构

```text
工作总览
组织与设备
├─ 区域与门店
├─ 员工与店长
└─ 设备管理
巡检业务
├─ 录音与转写
├─ AI巡检结果
├─ 申诉复核
└─ 员工业务记录
管理配置
├─ 基础报表
├─ 账号与权限
├─ 系统参数
└─ 操作审计
```

原有功能的归并规则：

| 当前功能 | 目标位置 |
|---|---|
| 设备绑定、设备运维 | 设备管理的台账、绑定、运行状态标签页 |
| 整改任务 | AI 巡检结果的状态、详情和整改区 |
| 知识库、巡检规则 | 系统参数的规则与知识标签页 |
| 接口日志、同步日志 | 操作审计的接口与同步标签页 |
| 荐药记录、培训 | 员工业务记录的荐药、学习、课程、任务与考试标签页 |

## 4. 核心业务需求

### 4.1 管理后台

- 登录：经理版品牌与版式；登录后按角色、区域、门店范围显示导航和数据。
- 工作总览：区域、门店、员工、设备、系统健康、门店表格；保留待复核、待整改、待申诉等闭环指标。
- 区域与门店：区域/门店增删改查、店长设置、批量导入导出、员工与设备数量。
- 员工与店长：员工增删改查、门店与角色分配、批量导入导出、微信绑定状态。
- 设备管理：设备台账、绑定关系、运行状态、绑定/调拨/解绑及审批状态。
- 录音与转写：列表、详情、音频授权访问、文本、ASR 服务商与状态、允许时重试。
- AI 巡检结果：经理版列表和详情；人工复核、推送整改、证据、修订与确认完整可见。
- 申诉复核：经理版双栏队列；显示原始证据、整改与申诉上下文，支持通过/驳回。
- 员工业务记录：荐药记录、学习记录、课程管理、培训任务与考试。
- 基础报表：按区域、门店、员工、时间筛选并导出，指标口径可追溯。
- 账号与权限：角色卡、权限矩阵、管理员账号、集团/区域/门店数据范围。
- 系统参数：ASR、AI 模型、队列阈值、保留周期、巡检规则和知识库。
- 操作审计：管理员操作、接口、同步和失败记录；支持筛选与详情。

### 4.2 培训中心

业务链路：

```text
巡检问题 / 合规规则 → 培训任务 → 课程 → 章节内容
                           ↓
                       学习进度 → 考试 → 成绩 / 通过
```

需要的数据实体：

- `learning_courses`：课程元数据、分类、封面、摘要、适用问题/规则、草稿/发布/归档状态。
- `learning_course_units`：有序图文、视频或链接章节，含时长和内容。
- `learning_tasks`：员工/门店分配、来源问题/规则、截止时间、完成和通过要求。
- `learning_progress`：员工与任务进度、最后位置、开始/完成时间和状态。
- `learning_exams`：课程考试定义、及格分、次数限制、考试时长和当前版本。
- `learning_questions`：题型、题干、选项、标准答案、分值、解析和排序；标准答案只允许服务端/授权管理员读取。
- `learning_exam_versions`：发布时冻结的试卷、题目、选项、标准答案和评分规则快照。
- `learning_attempts`：关联试卷版本的作答、逐题得分、总成绩、是否通过和提交时间。

课程发布后历史考试必须可追溯；进度和成绩受租户、门店和员工本人范围限制。

### 4.3 微信手机号登录

```text
wx.login 的 loginCode + getPhoneNumber 的 phoneCode
→ 服务端向微信换取身份与手机号
→ 按手机号匹配员工
→ 已匹配：绑定微信账号并登录
→ 未匹配：测试环境允许填写姓名/门店并建立测试关联；生产环境进入安全审核/关联流程
→ 返回当前系统认证令牌
```

新增 `wechat_accounts` 映射，至少包含租户、用户、员工、appid、openid、unionid、手机号、绑定状态和最后登录时间。测试环境可以使用明确标记的模拟 code；生产逻辑不得接受固定验证码或无校验自动建员工。

### 4.4 原生微信小程序

- 微信手机号登录、首次资料关联。
- 首页与待办、问题详情、整改反馈、申诉、设备、个人中心。
- 荐药记录。
- 学习首页、课程列表/详情、继续学习、考试、结果。

## 5. 体验与视觉要求

- 桌面管理后台忠实复现经理版的侧栏分组、顶部区域、卡片、表格、筛选区、状态标签和详情布局。
- 所有新页面必须有空状态、加载状态、错误状态和无权限状态，且使用同一视觉语言。
- 状态不能只依赖颜色；保留文字标签、键盘焦点和合理对比度。
- 密集表格在常用桌面宽度不得出现关键操作被遮挡；小程序负责移动端体验。

## 6. 数据与安全不变量

- 所有业务记录必须受租户与角色数据范围约束；员工只能访问自己的记录。
- 音频、转写、问题证据、申诉和培训成绩不得通过可猜 URL 越权访问。
- 任务领取、复核、申诉处理和设备绑定操作需要防重复提交与并发冲突。
- 不迁移经理预览库 `eyang.db`；后续如导入历史数据，必须使用显式 ETL、保留外部 ID，并让历史 AI 结果默认隐藏或待人工复核。
- 不复制经理包中的密钥、固定 ingest key、占位微信认证或无所有权校验的接口。

## 7. 非目标

- 本阶段不部署生产环境，不申请或写入微信生产密钥。
- 不接真实 ERP/药品主数据；荐药页需显示真实的数据来源状态，不能伪造已同步。
- 不整体迁移经理版 Python 服务、SQLite 数据库或静态后台。
- 不以删除当前闭环能力来换取页面一致。

## 8. 验收场景

1. 集团管理员登录后能按目标导航完成区域、门店、员工、设备、巡检、申诉、培训、权限和配置管理。
2. 区域或门店管理员只能看到授权范围，直接请求越权资源同样被拒绝。
3. 一条录音完成转写后进入 AI 疑似结果，经人工复核才能推送员工；员工可整改或申诉，后台可继续处理。
4. 管理员可从巡检问题创建培训任务，员工在小程序学习、考试，后台能看到可追溯的进度和成绩。
5. 测试环境可走微信手机号模拟登录；生产代码路径具备真实 code 交换与安全关联边界，未配置凭据时明确失败。
6. 管理后台主要页面在相同视口下与经理版结构一致，并通过空/加载/错误、键盘焦点和权限状态检查。
7. 仓库既有 `lint`、`typecheck`、测试、构建/verify 均通过；最终由 fresh context 审查并修复发现的问题。

## 9. 交付门禁

每个 Ticket 必须返回：改动文件、数据迁移/接口契约、自动化验证结果、浏览器或小程序截图、已知限制。所有 shell 命令必须经 `rtk`；功能实现至少执行对应定向测试，收口前执行 `rtk pnpm verify`。若工作区存在 `AGENTS.md`，同时遵守其中的额外门禁；修改后执行 `$code-review`，不得通过跳过测试或削弱断言获得通过。
